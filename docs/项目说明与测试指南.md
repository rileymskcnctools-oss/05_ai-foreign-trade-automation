## 1. 项目是做什么的

**外贸 AI 工作台**：面向手工农具（锄头、耙子、园艺工具等）出口业务，把外贸业务员的日常工作
用脚本 + 大模型串成自动化流程。

覆盖的业务链路：

```
产品数据整理 → SEO/详情页文案 → 市场调研 → 客户开发 → 开发信 → 报价 → 客户跟进 → 数据分析
     m1            m3              m4          m5/m8        m6        m7         m8          m9
```

技术上的定位：一个自研的 B2B 外贸业务中台。**它本身不是测试项目，而是自动化测试的"被测系统（SUT）"。**

## 5. 运行与数据复现

### 5.1 首次搭建（或换电脑）

```bash
# 1. 依赖（依 pyproject.toml 自动建 .venv，Python 3.12）
uv sync --extra dev

# 2. 复现数据库（建表 + 215 产品 + 演示数据）
python scripts/seed_db.py --reset

# 3. 前端构建
cd frontend && npm install && npm run build && cd ..

# 4. 启动
python run_web.py            # → http://localhost:8020 ，API 文档 /docs
```

### 5.2 数据库复现命令

```bash
python scripts/seed_db.py                  # 幂等：已有数据不重复灌
python scripts/seed_db.py --reset          # 重建表结构（DROP+CREATE）+ 重新灌
python scripts/seed_db.py --db <path>      # 指定库文件 ← 写测试时造独立数据用这个
python scripts/seed_db.py --products-only  # 只灌产品
```

### 5.3 环境变量

```bash
cp config/.env.example config/.env    # 填 DEEPSEEK_API_KEY 等
```

未配置 API Key 时，**所有不调 LLM 的接口可正常工作**；调 LLM 的接口会失败或降级。

## 7. 业务模块详解 m1~m9

### m1 产品库（`src/m1_product_db/`）— 不调 LLM（除 ai_completer）

| 文件 | 关键函数 | 说明 |
|------|----------|------|
| `importer.py` | `import_csv(filepath, encoding="gbk", db, dry_run)`、`import_excel(...)`、`normalize_col(name)` | CSV/Excel 导入，含中文列名别名映射（`产品编号`→`product_code`） |
| `exporter.py` | 导出 CSV / Excel（`engine="openpyxl"`） | |
| `search.py` | `search(query, db, limit)`、`filter_products(category=, sub_category=, material=, min_weight=, max_weight=, packaging_type=, status='active', limit, offset)`、`get_categories(db)`、`get_sub_categories(category, db)` | 关键词搜索 + 多维筛选 + 分页 |
| `cleaner.py` | `clean_product(product)`、`clean_all(db, category)`、`find_missing_fields(db, fields)` | 数据清洗 / 缺失字段检测 |
| `ai_completer.py` | 用 LLM 补全缺失字段 **[LLM]** | |

**导入器的一个关键行为**：内部用 `INSERT OR REPLACE`（按 `product_code` 去重），
所以重复导入是幂等的。

### m2 营销物料 — 不调 LLM
`catalog_generator.py`：用 fpdf2 生成 PDF 目录册、python-docx 生成 Word。

### m3 SEO 文案 — **[调 LLM]**
`alibaba_generator.py` / `website_generator.py` / `content_generator.py`：
生成阿里国际站标题/详情、独立站描述、卖点文案。

### m4 市场调研 — **[调 LLM]**
`report_generator.py` 生成国家市场报告；`knowledge_extractor.py` 抽取知识条目；
`web_researcher.py` 联网采集。

### m5 客户分级 — **[调 LLM]**

`grader.py` → `ClientGrader`：

```python
grade_client(client_id)          # 读库 → 组 prompt → 调 LLM → 更新 clients.grade/grade_score
grade_from_info(client_info)     # 不入库，直接评级
batch_grade(client_ids)
get_grading_history(client_id)
```

**重要行为**：LLM 调用失败时**降级**为固定结果
（各维度 5 分、`total_score=50`、`grade="C"`、summary 说明失败原因）。
→ 这是很好的测试点：**mock LLM 抛异常，断言降级结果**。

### m6 开发信 — **[调 LLM]**
`email_generator` / `whatsapp_generator` / `linkedin_generator` + `template_manager`（模板 CRUD，不调 LLM）。

### m7 报价 — **核心是纯算法，最适合单元测试**

`calculator.py` → `PriceCalculator`：

```python
get_price(product_code, market)                       # 查 price_records，无记录返回 None
set_price(product_code, base_price, min_price, market, notes)
calculate_price(product_code, quantity, market='', incoterm='FOB',
                currency='USD', margin_pct=15.0)      # ★ 主算法
calculate_loading(product_code, quantity)             # 装柜量（用 loading_qty_* 字段）
estimate_freight(total_cbm, market)                   # 运费估算
batch_quote(items, market='', incoterm='FOB', margin_pct=15.0)
```

`calculate_price` 的算法（摘自源码）：

```
1. 查产品；不存在 → 返回 {"error": "Product XXX not found"}
2. 查 price_records 取 base_price，没有则 base_price = 0
3. unit_price = round(base_price * (1 + margin_pct/100), 2)
   total_usd  = round(unit_price * quantity, 2)
4. total_weight = round(unit_weight * quantity, 2)
5. 体积：unit_cbm = length_m(硬编码0.5) * width_m(head_width_cm/100) * height_m(硬编码0)
6. incoterm == "CIF" 时附带 estimate_freight(total_cbm, market)
```

> ⚠️ 第 5 步有缺陷，见[第 12 节](#12-已发现的真实缺陷)。

### m8 CRM（`src/m8_crm/`）
`client_manager.py` → `ClientManager`：`create / get / update / delete / hard_delete / search /
list_all(status, country, grade, limit, offset) / count / change_status / pipeline_stats /
country_stats / recent_clients(days)`。
`activity_tracker` / `tag_manager` / `reminder` 均不调 LLM。
`browser_searcher.py`（Playwright）、`real_client_finder.py`（requests+bs4）**会访问外网**。

### m9 数据分析
`product_analytics.py` → `ProductAnalytics`：`overview / category_distribution /
material_distribution / surface_treatment_distribution / certification_stats /
handle_material_distribution / color_distribution / top_products(limit) / seo_coverage /
loading_capacity`。纯 SQL 聚合，**不调 LLM**。

## 9. AI 调用与 Mock 策略

### 9.1 LLM 客户端接口（`src/core/llm_client.py`）

```python
from src.core.llm_client import LLMClient, get_llm

client = LLMClient(provider="deepseek", scenario="market_research")
client.chat(prompt, system_prompt=None, max_tokens=4096, temperature=0.7) -> str
client.generate_json(prompt, system_prompt=None) -> dict     # 业务模块主要用这个
client.generate_list(prompt, system_prompt=None) -> list

# 便捷：按场景路由（config/settings.yaml 的 llm.routing）
llm = get_llm(scenario="seo_content")
```

provider 由 `config/settings.yaml` 的 `llm.default_provider`（当前 `deepseek`）决定，
场景路由把 `seo_content / market_research / client_analysis / outreach / quotation`
都指向 deepseek。

### 9.2 测试时的 mock 点

**关键结论：所有 LLM 调用都收敛到 `LLMClient.chat` 和 `LLMClient.generate_json`。**
只要 mock 这两个方法，就能在不联网、不花钱的前提下测所有含 AI 的接口。

推荐做法（思路，自行实现）：

- 用 `unittest.mock.patch` 打补丁到 `LLMClient.chat` / `LLMClient.generate_json`，
  返回**固定夹具数据**（JSON 字符串 / dict / list）。
- 给业务模块注入假的 client，而不是改环境变量。
- 需要测"AI 失败"路径时，让 mock 抛异常，断言降级行为
  （如 `ClientGrader` 降级为 `grade="C"`、`total_score=50`）。
- **不要**在测试里真连 DeepSeek：慢、不稳定、有费用、且结果不可断言。

需 mock 的接口：`/clients/api/{id}/analyze`、`/clients/api/generate-potential`、
`/clients/api/search-real-clients`、`/market/api/generate-report`、
`/outreach/api/generate-*`、`/quotation/api/ai-optimize`、
`/products/api/{code}/generate/{type}`。

## 10. 写测试：分层与环境准备

### 10.1 三层策略

| 层 | 目录 | 测什么 | 是否需 mock LLM | 速度 |
|----|------|--------|----------------|------|
| 单元 | `tests/unit/` | 纯逻辑：`PriceCalculator`、`cleaner`、`ClientManager`、分析器聚合 | 否 | 毫秒 |
| 接口 | `tests/api/` | 47 个 HTTP 端点：状态码、响应结构、业务断言、异常分支 | 部分需要 | 百毫秒 |
| UI | `tests/ui/` | 7 个 Vue 页面的关键交互（Playwright） | 是（页面会拉数据） | 秒级 |

**建议顺序**：单元（打好基础）→ 接口（核心战场）→ UI（加分项）。

### 10.2 测试数据方案（重要）

**不要直接在 `data/ft_workspace.db` 上跑写操作类测试**——会污染开发库、用例之间互相干扰。

正确做法：给每个测试会话/模块造一个**独立的临时库**：

```bash
python scripts/seed_db.py --db <临时路径> --reset
```

然后在 fixture 里把应用的 `get_db()` / `FTDatabase` 指向它。
`FTDatabase(db_path=...)` 支持传路径，`web/deps.py` 的 `get_db()` 是依赖注入点。

### 10.3 环境准备

```bash
uv sync --extra dev                       # pytest + httpx + pytest-cov
.venv\Scripts\python -m pytest            # 全部
.venv\Scripts\python -m pytest -m smoke   # 只跑冒烟
.venv\Scripts\python -m pytest --cov=src --cov-report=term-missing
```

已注册的 marker：`smoke` / `api` / `ui` / `unit` / `slow`
（`pyproject.toml` 已启用 `--strict-markers`，用未注册的 marker 会**收集报错**）。

### 10.4 测接口的两种姿势

```python
# 姿势 A：进程内 TestClient（快，推荐先掌握）
from fastapi.testclient import TestClient
from web.main_api import app
client = TestClient(app, raise_server_exceptions=False)   # 默认 True 时异常会直接抛出
r = client.get("/clients/api/1")
```

> 提示：`raise_server_exceptions=True`（默认）下，服务端 500 会以**异常**形式冒泡，
> 而不是返回 500 响应。想断言状态码，要显式传 `raise_server_exceptions=False`。

```python
# 姿势 B：真实起服务再打 HTTP（更接近生产，用于 UI/联调）
# 先 python run_web.py，再 requests.get("http://127.0.0.1:8020/...")
```

### 10.5 断言要有层次

一个接口用例至少覆盖三层，只断 `status_code` 是远远不够的：

```
① 协议层：status_code、Content-Type
② 结构层：字段存在性、类型（如 clients 是 list、id 是 int）
③ 业务层：字段值符合业务语义（id 与请求一致、company_name 非空、
          分页 limit 生效、统计值等于数据库实际值）
```

## 12. 已发现的真实缺陷

> 这些是真实存在的缺陷（部分已修），可直接作为测试用例的参考，也是面试时的谈资。

### 缺陷 1（已修）：`/analytics/api/products` 返回 500

- **现象**：`sqlite3.OperationalError: no such column: color`
- **根因**：库的 `products` 表还是旧结构（有 `length_cm`、无 `color`），
  而 `schema.sql` 用 `CREATE TABLE IF NOT EXISTS`——表已存在就不会更新结构。
- **修复**：`seed_db.py --reset` 改为 DROP + CREATE，从机制上对齐结构。

### 缺陷 2（已修）：`/quotation/api/stats` 返回 500

- **现象**：`sqlite3.OperationalError: no such column: profit_amount`
- **根因**：V4 需要的 22 个报价字段 + `quotation_items`/`quotation_versions` 两张表，
  原本写在外挂补丁 `data/quotation_upgrade.sql` 里，从未合并进 `schema.sql`——
  **schema 有两个真相源**，新环境建出的库必然缺列。
- **修复**：合并进 `schema.sql` 并删除外挂补丁。

### 缺陷 3（未修，仍在）：报价体积计算恒为 0

- **位置**：`src/m7_quotation/calculator.py` 的 `calculate_price`
- **现象**：代码里 `length_m = 0.5`（硬编码）、`height_m = 0`（硬编码注释说"表里没有高度列"），
  于是 `unit_cbm = 0.5 * width * 0 = 0`，`total_cbm` 恒为 **0**。
- **影响**：CIF 报价的运费估算 `estimate_freight(total_cbm=0, ...)` 必然失真。
- **根因**：`length_cm` 列被历史迁移删掉后，体积计算没有同步改造。
- **建议用例**：断言 `calculate_price(..., incoterm="CIF")` 返回的 `total_cbm` ——
  当前会得到 0，这正是缺陷的暴露点。

### 缺陷 4（文档类，已修）
- README 曾声称 215 产品但库为空；端口 8001/8005/8011 三处不一致；
  技术栈仍写 HTMX/Python 3.13；引用不存在的 `archive/`；`requirements.txt` 曾不存在。

### 隐患 5（未修）：`google-generativeai` 已停止维护
- 启动时抛 `FutureWarning`，官方建议迁移到 `google.genai`。

## 13. 常见坑

1. **导入路径**：项目用 `from src.xxx` / `from web.xxx`，依赖项目根在 `sys.path`。
   `pyproject.toml` 已配 `pythonpath = ["."]`，从项目根运行 pytest 即可。
2. **数据污染**：直接在开发库上跑写操作测试，会破坏后续用例。用 `--db` 造临时库。
3. **TestClient 吞掉 500**：默认 `raise_server_exceptions=True`，500 会变异常。
4. **中文编码**：产品 CSV 原始文件是 GBK；仓库里已转 UTF-8
   （`data/seed/products.csv`）。导入历史 GBK 文件要显式传 `encoding="gbk"`。
5. **唯一约束**：`products.product_code`、`quotations.quotation_no` 是 UNIQUE，
   重复插入走 `INSERT OR REPLACE`（产品）或报错（报价）。
6. **外键**：`FTDatabase` 开启了 `PRAGMA foreign_keys=ON`，
   删客户前要先处理引用它的 activities/quotations。
7. **AI 接口不可确定性断言**：断言结构与字段存在性，不要断言具体文案。
8. **端口漂移**：V3=8011、V4=8020、前端 dev=5173；README 里的 8001 是历史遗留。
9. **`config/.env` 缺失**：不影响非 AI 接口，但会让 AI 接口失败/降级。
